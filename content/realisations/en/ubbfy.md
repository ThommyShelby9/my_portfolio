## The challenge

Ubbfy ran on a five-year-old Django monolith: server-rendered templates, few tests, and enough debt that adding one module broke others. Time tracking, inventory, HR, projects and helpdesk all lived in the same codebase.

The brief fit in three lines. Rebuild without taking production down. Migrate one module at a time. Ship, in parallel, a mobile app for geolocated time tracking on remote sites, where a worker starting a shift at 6 a.m. cannot wait for the app to make up its mind.

## Key features

- **A web back office** in Vue 3 and PrimeVue, split into 16 business modules, including employees, payroll, recruitment, billing, documents, support and statistics. TanStack Table for heavy lists, Leaflet for maps, ApexCharts for charts.
- **Geolocated clock-in** with the Flutter app `ubbfypresence`: a configurable radius around each site, an optional photo, instant start thanks to cached site coordinates, and one account per device so colleagues cannot clock in for each other.
- **Offline mode**: with no network, the clock-in is stored encrypted on the phone and synced when the connection returns.
- **A live presence screen** showing who clocks in, as it happens.
- **Documents**: payslips and contracts generated as PDF, Excel exports, S3-compatible storage.
- **Notifications**: Web Push in the browser, FCM on mobile, SMS as a fallback.

## Constraints and decisions

- **One API as the single source of truth.** I set one rule from day one: no business logic in the clients. The web app, the PWA and the Flutter app all consume the same DRF API, whose OpenAPI contract is generated by drf-spectacular. A business rule changes in one place and all three clients follow.
- **The strangler pattern instead of a big-bang switch.** Each rebuilt module unplugs its legacy counterpart through a per-company feature flag. Companies move over one at a time, with one-click rollback. Slower on paper, but no payroll run is ever put at risk by a migration.
- **A batch clock-in endpoint.** The first Flutter version called the REST API through a home-grown cache layer. With 50 people clocking in at once on the same site, it saturated. I replaced that call with a dedicated endpoint, `/api/attendance/checkin-batch/`, with server-side deduplication and deferred acceptance.
- **Long tasks outside the request.** PDF generation (WeasyPrint), exports and imports run on Celery; periodic jobs (daily reports, monthly payroll close, invoice reminders) on django-celery-beat. Real-time updates go through Channels and Redis. Sentry covers both the back end and the mobile app, correlated by user, so a Flutter incident can be replayed from the Django trace.

## Outcome

The platform is in production at app.ubbfy.com and the rebuild continues, one module at a time. 20 Django apps now serve three clients from a single API.

The most valuable month of the project was not a technical one: I spent it designing the admin screens with the client’s HR lead. An ERP rebuild is won first on how readable the back office is. If HR, accounting and operations cannot do their work in the new interface within the first two weeks, no amount of code quality underneath will save it.
